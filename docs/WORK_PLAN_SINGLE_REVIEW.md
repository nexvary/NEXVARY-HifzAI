# NEXVARY HifzAI — الخطة التنفيذية النهائية | One-Submission Work Plan
**Version:** 1.0 • **Date:** 2026-10-14 • **Base:** 0.3.0-dev, branch `dev/foundation`
**Decision:** لجنة العلماء تتلقى **طلبًا رسميًا واحدًا فقط**، بعد إنهاء التطبيق واختباره وتجهيز ملف الاعتماد. **ممنوع إرسال نسخ جزئية للجنة.**

## 1. تعريف «المشروع انتهى»
المقصود هو **Feature-complete candidate**: جميع الوظائف المتفق عليها تعمل فعلًا، الكود والاختبارات والمصادر والحقوق مكتملة، واجهات لا تحتوي على أزرار وهمية، وبناء قابل لإعادة الإنتاج واختبار على أجهزة حقيقية. لا تعني الجاهزية التقنية أن النص أو المنهج معتمد شرعًا؛ تلك الموافقة لا تحصل إلا بعد تقديم النسخة النهائية للجنة.

لا يتم الادعاء بأن الوظائف «مكتملة» لمجرد وجود كود أو نجاح Build. مستوى الحالة: `Not started` / `In progress` / `Code complete` / `QA verified` / `Ready for single committee submission` / `Committee approved` / `Released`.

## 2. الحوكمة: تقديم علمي واحد
- **قبل التقديم:** تطوير وتجريب داخلي واختبارات برمجية وهندسية وتدقيق محتوى وحقوق وعرض قرآني *داخل الفريق*؛ يمكن الاستعانة بمختصين داخليين لمراجعة الجودة دون مخاطبة اللجنة الرسمية.
- **لن يرسل:** رسائل متتابعة، معاينات أولية أو طلبات اعتماد جزئي إلى لجنة العلماء. المستند الحالي مجرد تحضير داخلي.
- **قرار الجاهزية:** صاحب المشروع يصرح بالتقديم بعد إغلاق كل المشكلات الحرجة ومعه تقرير الأدلة والنسخة النهائية.
- **محتويات الطلب الواحد:** APK/AAB مرشح للتقييم مع بصمة SHA-256، مراجعة UI، المستودع وcommit ثابت، توثيق المصحف والرواية، أذون التسجيلات، شرح الميزات والمنهج، حالات اختبار مثبتة، مخاطر معروفة، بيان استعمال AI وعدم اليقين، فهرس المراجع، ودليل عربي مبسط.
- **في حال رفض اللجنة أو طلبها تعديلًا:** لا يجوز تفسير التقديم الوحيد على أنه موافقة. يظل النشر محجوبًا؛ يُطبَّق قرار اللجنة ويُسأل صاحب المشروع عن إمكان الإجراء اللاحق، دون افتراض جواز طلب مراجعة ثانية.

## 3. ترتيب التنفيذ: موجات مترابطة لا تقارير وهمية

### W0: تثبيت الأساس والتزامات المصدر المفتوح
**التسليم:** ترخيص MIT للكود المؤلف خصيصًا للمشروع؛ NOTICE لحقوق القرآن والصوت والخطوط؛ README دقيق؛ سياسات المساهمة والأمان؛ إصلاح التسمية `0.3.0-dev-dev`؛ فروع PR؛ CI صالح؛ قائمة الأصول وتراخيصها.
**قبول:** يمكن لأي مساهم رؤية الترخيص وحدود الاستثناءات، وإعادة البناء، والإبلاغ عن الثغرات؛ لا secrets ولا ملفات غير مأذون بها في المستودع.

### W1: المصحف الكامل الموثّق (مسار حرج)
**التسليم:** مصدر مرخّص موثوق لرواية محددة (بدايةً حفص عن عاصم، بشرط ثبوت المصدر والرسم)، 114 سورة، فحص أرقام 6236 آية وفق هذا العد، checksum مستقل؛ renderer عربي/عثماني يحفظ الرسم والضبط/الوقف/البسملة؛ بحث/فهارس منفصلة عن النص القانوني الثابت؛ قائمة المصادر والإصدارات.
**قبول:** مراجعة آلية حرفية على كامل الملف + مقارنة مستقلة بمصدر أصل معتمد؛ تدقيق شاشة المصحف بصريًا ونصيًا بواسطة مختص داخلي، دون تغيير كلمة أو حرف أو علامة في corpus؛ لا إطلاق مع اختلاف غير محلول.

### W2: محرك حفظ مبتكر متكامل
**القدرات:** القراءة والاستماع، سُلّم الإخفاء (0/35/70/100%)، اختبار التسميع من أي موضع، ربط السابق باللاحق، كلمات مفتاحية استدعائية (موسومة تلميحًا)، تدريب المتشابهات من فهرس مقارن لا يبدل الأصل، بصمة ذاكرة شخصية، خطط يومية، تكرار موجه لأضعف المواضع، جلسات مراجعة مؤجلة، وضع حفظ بالصوت دون تصحيح مزعوم، إنجازات غير مضللة.
**قبول:** مسارات عملية لكافة الحالات، تفريق واضح بين استرجاع مستقل ومساعدة أو كشف، اختبارات تراجع للآية والصفحة والسورة والأخطاء والمتشابهات، ومراجعة تربوية تجريبية داخلية.

### W3: تلاوات مشايخ مصر والسعودية
**التسليم:** ملفات تعريف مدققة، فصل القارئ عن المعلم، سجل حقوق مستقل لكل مصدر وتسجيل، تشغيل سورة/آية/مقطع، التكرار والبطء والتوقف والخلفية والتحكم من السماعة، تنزيل وفق الترخيص، اختيار الرواية بدقة، مزامنة الآية بالصوت عند ثبوت التوقيت.
**قبول:** لا زر تشغيل بلا محتوى مرخّص؛ لا تنسب قراءة أو رواية إلى شيخ خطأ؛ لا تحميل غير مصرح؛ اختبارات اتصال ضعيف/خلفية/استئناف.

### W4: التسميع والتحليل الصوتي الموثوق
**التسليم:** تسجيل اختياري بموافقة واضحة، مقارنة ترتيب الكلمات مع مرجع موثق على نحو تجريبي، مستوى ثقة، عرض «غير قادر على الحكم» عند الشك، إمكان المراجعة البشرية، الفصل الصريح بين مطابقة الكلمة والتجويد والمخارج.
**قبول:** مجموعة تقييم صوتية مرخصة ممثلة، مقاييس false positives/false negatives منشورة في ملف المشروع، اختبارات الحالات الحدية والروايات؛ لا تمكين تصحيح التجويد كحكم قاطع دون أدلة وعتبات تُعرض على اللجنة في التقديم النهائي.

### W5: أكاديمية المشايخ وإدارة المستخدمين
**التسليم:** تسجيل والتحقق من المدرسين بصفة تشغيلية لا اعتراف شرعي مفترض، ملفات طلاب ومواعيد وجلسات، لوحة إدارة، صلاحيات ولي الأمر، سجل تقدم، حماية الأطفال، بلاغات وإيقاف الاتصال، خصوصية وحق الحذف.
**قبول:** اختبار صلاحيات وأمان واعتداءات واختبار عدم تجاوز أدوار المستخدمين؛ لا شهادة إجازة قرآنية يصدرها البرنامج نفسه دون توثيق فعلي.

### W6: تصميم فاخر وبديهي يمر باختبار قابلية الاستخدام
**التسليم:** نظام التصميم في `docs/LUXURY_UI_UX_SPEC.md`، شاشات البداية، اختيار الشيخ، المصحف، جلسة الحفظ، الخطة اليومية، التقدم، المتشابهات، المعلم، الإعدادات، الأخطاء والتحميل، المساعدة.
**قبول:** Arabic RTL أصيل، نص قرآني مقروء دون زينة تعيقه، مساحات واضحة، حجم عناصر لمس مناسب، رموز SVG/Vector حقيقية، رجوع داخلي، دعم الخط الكبير وTalkBack، عدم قص عناصر على هواتف وتابلت، صور حقيقية لكل شاشة في تقرير QA.

### W7: اختبارات شاملة وتجربة فعالية الحفظ
**التسليم:** Kotlin/JVM + Android Instrumentation/Compose UI + screenshot baselines + fuzz لحدود الآيات + اختبارات مصدر المصحف + اختبارات الصوتيات/الحقوق/الخصوصية + تقرير أمن وDependency SBOM + اختبارات أندرويد 15 وأجهزة أخرى + قياس الذاكرة/البطارية + تثبيت وتحديث وحذف بدون فقد غير مبرر.
**قبول:** جميع اختبارات التوقف الحرجة خضراء، لا bug معروف يغيّر نصًا أو يشوش رواية أو ينشر حقوقًا أو يخرق الخصوصية؛ عدم الادعاء بضمان صفر أخطاء. تجربة تذكر/مراجعة مع مستخدمين تحت إشراف وتوثيق النتائج كبيانات لا كتسويق.

### W8: إصدار مرشح نهائي وملف التقديم الواحد
**التسليم:** Freezed release candidate مع رقم إصدار وSHA-256، changelog، كود مفتوح مطابق، license/notice، دليل استخدام عربي، screenshots، مصفوفة المتطلبات و219 رقم مرحلة مع حالة حقيقية، تقرير CI وأجهزة، سجل أخطاء مغلق/مؤجل بمبرر، ملف المحتوى والحقوق، قائمة مراجع الذكاء الاصطناعي ومحدوديته، محضر فحص جودة داخلي.
**قبول:** توقيع صاحب المشروع على قرار «جاهز لطلب اللجنة الرسمي الواحد» بعد تدقيق نهائي. **قبل هذا القرار لا نرسل التطبيق للجنة ولا ندّعي اعتمادها.**

### W9: قرار اللجنة ثم سياسة النشر
**التسليم:** استقبال نتيجة اللجنة مرة واحدة والالتزام بها؛ النشر إلى المستخدمين فقط إذا وافقت وفق نطاق واضح وبعد اكتمال أي موافقات قانونية وحقوقية لازمة؛ قناة للإبلاغ والتصحيح والتراجع.
**قبول:** إذن مكتوب قابل للتوثيق، بلا تعميم خارج نطاقه؛ عدم افتراض موافقة بسبب السكوت.

## 4. معايير تصميم إلزامية
- هوية Royal Navy/Black مع ذهبي معتدل وفضي ولمسة أخضر زمردي، دون بهرجة على النص القرآني نفسه.
- مصحف واضح أولًا؛ لا مزاحمة بالأزرار أو الموجات البصرية في منطقة الآية.
- 4–5 وجهات رئيسية ثابتة، وباقي الخيارات في صفحات منظمة؛ لا صفحات طويلة مزدحمة.
- CTA رئيسي واحد لكل شاشة، لغة عربية بسيطة، شرح مختصر ومؤشرات تقدم صادقة.
- تنقل داخلي واضح، وضع سهل للمبتدئ ومتقدم اختيارياً؛ لا أيقونة بلا وظيفة.
- التلاوة والتسميع لا يفعّلان أذونات حساسة قبل إيضاحها والموافقة عليها.

## 6. متابعة العمل يوميًا داخل GitHub
- `dev/foundation` أساس عمل؛ تغييرات محددة عبر PR وأسماء واضحة؛ لا إعادة تعيين عشوائية للفرع أو حذف الوظائف السليمة.
- كل Issue يحتوي: المتطلب، الاعتماديات، خطورة الخطأ، مخرجات قابلة للفحص، الاختبار والدليل، ومالكه عند تعيينه.
- Feature Flags للميزات غير المكتملة، لا تُظهر زرًا نشطًا وهميًا.
- تمييز مراحل `docs/PHASES_002_220.md` كـ backlog؛ لا تغيّر مربعات الإنجاز دون أدلة محددة.
- CI لا يساوي موافقة شرعية، وأذونات API لا تساوي ترخيصًا عامًا لإعادة التوزيع.

## 7. ترتيب التنفيذ الأول المعتمد
1. ترخيص المصدر المفتوح + مواصفات التصميم + سياسة المراجعة الواحدة.
2. تدقيق آخر build وتثبيت SHA-256 وتحديث نسخة التطبيق وتصحيح README.
3. تخطيط مصدر المصحف ومقارنته ثم renderer والتحقق المستقل قبل إدخاله في كل التجارب.
4. استكمال شاشات تجربة الحفظ الفاخرة واستقلال نماذج المصدر والتمارين.
5. الوظائف الصوتية والقراء ثم التسميع، مع عزل ما لا يمكن قياسه بأمان.
6. أكاديمية المعلمين والخصوصية ثم QA شامل ثم تحضير حزمة اللجنة **مرة واحدة**.

**لا تاريخ نهائي مصطنع؛ انتقال كل موجة يتوقف على إنجازها ومعايير الجودة.**
